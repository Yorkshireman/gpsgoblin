# How public browser FIT converters decode files

Checked **20 September 2026**. This is point-in-time implementation research for [ticket #55](https://github.com/Yorkshireman/gpsgoblin/issues/55), not legal advice or approval to adopt a dependency. It inspects first-party pages, the JavaScript those pages served, and upstream package source/licences. A minified bundle can establish code and API fingerprints, but not private source history, authorisation, licence compliance or the legal basis on which another operator acts.

## Answer

The inspected sites do not reveal one industry-wide solution. They use three approaches:

1. **A permissively licensed parser:** FormatFixer explicitly imports `fit-file-parser@2.3.3`; TrailSplits bundles code with the same `FitParser` API and output shape.
2. **A small decoder written for the site's narrow conversion needs:** AvoMap and Epic Efforts walk the FIT binary with `DataView` and recognise selected global messages and fields.
3. **A broad custom or modified decoder of unknown provenance:** FIT File Viewer serves its own substantial parsing/recovery code and profile tables, but its public assets do not identify a package or provide enough provenance to classify it as Garmin's SDK, a permissive parser or wholly independent code.

There was no positive public-code fingerprint for Garmin's published `@garmin/fitsdk` decoder API in the five sites inspected. That does **not** prove that none of their code or profile data originated from Garmin materials, nor that any operator's use is licensed. Other sites' behaviour does not resolve GPSGoblin's dependency gate.

## What the two identifiable choices imply

[`fit-file-parser`](https://www.npmjs.com/package/fit-file-parser) accepts `ArrayBuffer` input in browser-style code and exposes the records and session/lap structures these converters consume. Its [upstream repository](https://github.com/jimmykane/fit-parser) and [licence](https://raw.githubusercontent.com/jimmykane/fit-parser/master/LICENSE) identify it as MIT-licensed; the npm registry's [metadata for the exact 2.3.3 release](https://registry.npmjs.org/fit-file-parser/2.3.3) also declares MIT and supplies the tarball integrity digest. The MIT grant permits use, modification and distribution subject to retaining its copyright and permission notice in copies or substantial portions.

That package-level declaration does not finish the provenance review. The current repository's [profile generator](https://github.com/jimmykane/fit-parser/blob/main/codegen/garmin-profile.ts) imports `Profile` from `@garmin/fitsdk`, and the committed [generated profile](https://github.com/jimmykane/fit-parser/blob/main/src/garmin_profile.generated.ts) says it was generated from a named Garmin SDK version. The current package and the old `2.3.3` used by FormatFixer must therefore be assessed as actual dependency artifacts, including the origin and distribution terms of their profile tables; package metadata is not a substitute for inspecting the installed tarball, transitive dependencies and bundled notices. This research does not conclude whether generated protocol facts are protected or whether the package maintainers have separate permission.

The small bespoke decoders demonstrate why a basic converter can exist without a general FIT SDK: a site can implement the FIT container mechanics and a short list of message/field numbers, then emit positioned records as GPX. That shortcut has an important product boundary. AvoMap's public chunk, for example, handles only four global message types and does not interpret developer fields. It is evidence of a narrow implementation, not evidence that a hand-written decoder would meet ticket #55's subtype validation, session/segment preservation, integrity, corruption and representative-device requirements.

Garmin's official [JavaScript SDK](https://github.com/garmin/fit-javascript-sdk) is browser-capable and documents the `Decoder`, `Stream`, `Profile` and `Utils` API. Its source is covered by Garmin's [FIT Protocol License Agreement](https://github.com/garmin/fit-javascript-sdk/blob/main/LICENSE.txt), not MIT. The agreement's text limits the grant to internal business purposes and restricts making the licensed technology or its functionality available to third parties. This research does not give a legal conclusion about a particular deployment, but it confirms that competitor existence is not evidence that this licence is suitable for GPSGoblin.

## Evidence gaps and implementation consequence

- Served bundles can be replaced, minified or stripped of names. The observations above identify current code paths, not a permanent dependency inventory.
- No network upload of a personal FIT file was performed. Browser-only processing is supported by the providers' pages and visible code paths, not by a complete runtime traffic/privacy audit.
- No converter output was accepted as a correctness oracle. None of the competitors' field selection or recovery behaviour establishes GPSGoblin's required preservation policy.
- No claim is made that a site complies or fails to comply with a licence. Public code cannot reveal private permissions or independently developed source provenance.
- FIT File Viewer's profile tables and advanced recovery code warrant caution: public evidence is insufficient to use it as precedent for either Garmin SDK redistribution or independent implementation.

The practical next dependency candidate is therefore the actual `fit-file-parser` release GPSGoblin would install, not Garmin's SDK and not copied competitor code. It still needs the ticket's browser/worker/Jest, package-integrity, bundle-size, memory, profile provenance, malformed-input and representative-fixture evaluation before adoption. If it fails those checks, a deliberately narrow independent decoder would be a new engineering and compatibility decision, not a licence workaround inferred from competitor behaviour.
