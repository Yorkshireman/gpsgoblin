# Remaining FIT decoder options

Checked **20 September 2026** for [ticket #55](https://github.com/Yorkshireman/gpsgoblin/issues/55). This note assumes no answer from Garmin and excludes both Garmin's official JavaScript SDK and `fit-file-parser@5.2.1` from adoption. The latter's exact-artifact provenance is covered in the [separate licence audit](fit-file-parser-license-research.md).

This is an engineering and dependency-risk assessment, not legal advice. An open-source licence on a parser establishes the author's offer for that code; it does not by itself establish the author's right to relicense Garmin-derived profile material.

## Decision

There is no maintained, browser-ready third-party decoder in the reviewed set that both meets ticket #55's correctness boundary and has a demonstrably independent, redistribution-compatible profile-data trail. Chasing another package is therefore not a useful next step.

Two paths remain worth owner consideration:

1. **Time-box a genuinely independent, deliberately narrow decoder feasibility spike.** Decode the FIT container generically, but interpret only the small activity subset ticket #55 requires. Do not copy a full Global Profile, generated table, SDK implementation or competitor parser. Keep a field-by-field provenance record and obtain qualified legal review if the source of the necessary protocol facts cannot be shown to be independently usable. This is the only FIT path worth further engineering before Garmin replies.
2. **Defer #55 and assess TCX-to-GPX or another commercially evidenced task.** The product specification explicitly leaves FIT-versus-TCX order unresolved. TCX is XML, so a bounded converter can use the browser's XML facilities without distributing a FIT SDK or Global Profile table. It still needs its own schema/licence, fixture, preservation and demand assessment; lower engineering risk is not evidence of greater search demand.

The recommended immediate choice is **defer public FIT implementation unless the owner explicitly accepts a bounded decoder spike**. The spike must stop before UI work if it cannot pass the gates below. If avoiding unresolved format-licensing risk is the priority, reassess TCX-to-GPX rather than weakening ticket #55's acceptance criteria.

## What a narrow independent spike must prove

Garmin's public [protocol description](https://developer.garmin.com/fit/articles/fit-protocol/fit_protocol.html) confirms that a FIT file carries definition messages describing byte layout, followed by data messages, while the separately maintained Global Profile supplies message and field meaning. This makes a profile-free binary reader possible, but not a useful converter by itself: ticket #55 still needs a small semantic mapping for activity subtype, sessions, laps/events, coordinates, timestamps and elevation.

Before any page or converter UI work, a spike must demonstrate all of the following against public-safe or permissioned known-answer fixtures:

- strict header, declared-size, definition/data alignment and file CRC validation;
- both byte orders, compressed timestamps, invalid sentinels and safe skipping of unknown/developer fields;
- positive activity-subtype identification and explicit rejection of course, workout and settings files;
- preservation of source order and reliable association of records, laps, events and multiple sessions without merging them;
- exact coordinate, timestamp and elevation conversion for the small supported field set;
- failure on truncation/corruption instead of recovery presented as complete success; and
- a written provenance entry for every semantic constant and conversion rule, without importing a generated Global Profile.

Passing these gates would establish technical feasibility, not legal clearance or broad device compatibility. If a required mapping can only be obtained by copying Garmin's SDK/profile material, stop and seek legal advice rather than recreating the rejected table in miniature.

## Why deferring to TCX is rational, but not automatic

The [product specification](product-spec.md#33-current-short-to-medium-term-priority--agreed) says FIT-versus-TCX order is undecided and requires the strongest commercial next action after the example experience. The existing [commercial review](commercial-review.md#current-recommendation) gives FIT-to-GPX only low commercial confidence: demand, rankings and profit are unverified, while free competitors already exist.

TCX removes the binary container and Global Profile dependency from the implementation. A browser can parse the user's XML locally, and Garmin publishes the [`TrainingCenterDatabasev2.xsd`](https://www8.garmin.com/xmlschemas/TrainingCenterDatabasev2.xsd) that defines the document structure. A TCX converter would still require a separate decision on using or reproducing anything from Garmin's schema, independent fixtures, namespace/subtype validation and preservation rules. It should therefore be proposed as a new bounded ticket, not silently substituted into #55.

Lower technical and dependency risk makes TCX-to-GPX a rational candidate if FIT is deferred. It does **not** establish that TCX has more reachable demand than FIT, nor that either converter outranks an evidenced GPX acquisition or correctness task. That choice belongs in the repository's commercial “what next?” review with current Search Console and issue evidence where available.
