# Large GPX import profiling — issue #4

Historical slice report. The [large-file completion report](large-file-support.md)
supersedes its outstanding implementation work and records final evidence.

Measured 12 September 2026 at commit `9b27be2`, before chart display reduction.
See the [chart performance follow-up](chart-performance.md) for the subsequent implementation and measurements. **Issue #4 remains open.** The current code accepts
large recordings, but long main-thread pauses mean large-file responsiveness is
not complete. No deployment or broad device-support claim follows from this report.

## Product decision

Large recordings are an intended use case. The owner's complete 8,142-point,
roughly 2.5-hour activity is an ordinary baseline. All-day, multi-day and densely
sampled activities must inform the work. The previously proposed 2 MiB / 5,000-point,
XML complexity, structure-count and five-second cutoffs were not approved and have
been removed. A benchmark workload or automation timeout is not a product limit.
Any hard resource restriction requires explicit owner discussion and agreement,
with evidence and workarounds considered first. O4 remains unresolved.

The viewer still opens one document at a time. Malformed XML, DOCTYPE declarations,
unsupported GPX versions and missing geographic data receive explicit errors.
Imports run in a dedicated worker with request IDs, stale-result protection and
user cancellation; replacement, clear and unmount terminate pending work. A long
import is no longer stopped by a fixed processing deadline. Browser memory remains
finite; no configured cap is not a promise of unlimited capacity or responsiveness.

## Method and reproduction

- Apple M2, 16 GiB RAM, arm64; macOS 26.6.2 / Darwin 25.6.0.
- Google Chrome 153.0.8010.36, headless; Node 24.20.0, pnpm 12.3.4.
- Production static export, local HTTP server; no remote basemap.
- Desktop content viewport 1280×720. Three fresh pages per workload at native CPU
  and CDP 4× **page CPU** slowdown. Worker CPU is not equivalently throttled.
- Local file paths are supplied to the picker. No base64 upload buffer is allocated
  inside the page. The original recording is only read; it is not copied to artifacts.
- CPU profiles are recorded during import. Timing includes profiling overhead.
  Import completion is a loaded position control followed by two animation frames;
  it is a chart-paint proxy, not a guarantee that the map worker has finished drawing.
- Worker round trip includes startup, file reading, parsing, result cloning and
  delivery. Browser transfer-only time is not isolated. Post-worker time includes
  analysis, display preparation, React/Recharts, layout and frame scheduling.
- The largest Long Task entry is measured during import, not the later interaction.
  Selection latency measures keyboard ArrowRight through visible selected values
  and two frames; it includes automation scheduling, not just handler execution.
- Page heap is a CDP sample after import, **not peak memory**, total browser memory,
  worker heap, GPU allocation or a physical-phone measurement.

Run `pnpm build`, then serve `out` on `127.0.0.1:4173`. In another terminal:

```sh
pnpm benchmark:imports
pnpm profile:imports
```

`GPX_VERIFY_FILE` optionally names a private local GPX file. Output uses only the
label `private-recording`; it omits its path and contents. The parser-phase command
uses the synthetic files generated by the browser benchmark. `GPX_BENCHMARK_POINTS`,
`GPX_BENCHMARK_RUNS`, `GPX_CPU_RATES`, `GPX_PHONE`, `GPX_BENCHMARK_CASE` and
`GPX_PROFILE_DIR` configure this investigation. Defaults are 10k/50k/100k/250k
points, three runs, native and 4× page slowdown, with artifacts in
`/tmp/gpsgoblin-profiles`. The 60-second Playwright timeout bounds automation only.
A failed case must be recorded as a failed investigation, never relabelled as an
application resource limit. CPU profile files contain function names and static
asset URLs; do not publish unrelated browser traces or private screenshots.

Coarse results are retained in [desktop trials](benchmarks/largeImportsDesktop.jsonl),
[phone-viewport trials](benchmarks/largeImportsPhone.jsonl) and
[Node pipeline trials](benchmarks/largeImportsPipeline.jsonl). They contain no source
coordinates, timestamps, filenames or paths.

## Isolated pipeline costs

`pnpm profile:imports` transpiles trusted repository modules in a separate Node
process and times the actual parser, structured clone, analysis and chart-data
conversion. Parser methods are instrumented only in that process; no production
source files are instrumented. Three runs, milliseconds:

| Input | XML validation | XML DOM construction | Adapter/extraction remainder | Clone | Analysis | Smoothing + display conversion |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Complete private recording | 22–36 | 195–292 | 45–61 | 6 | 7–9 | 3–4 |
| 10,000 points | 13 | 107–108 | 41–44 | 6–7 | 7–8 | 3–4 |
| 50,000 points | 49–53 | 493–507 | 199–219 | 32–36 | 36–41 | 7–10 |
| 100,000 points | 99–104 | 989–1,020 | 411–416 | 62–65 | 79–87 | 12–15 |
| 250,000 points | 252–261 | 2,547–2,614 | 981–989 | 179–204 | 187–215 | 22–38 |

This is phase isolation, **not Chrome timing**: Node's DOM construction is notably
slower than the browser worker round trip. Do not add these values to browser
measurements. Validation is a strict SAX pass; DOM construction is a second XML
pass. The adapter remainder includes traversal, validation, object creation and
measurement overhead. Heap sampled just after parsing 250k points reached about
1.1–1.3 GiB in this Node harness, including uncollected DOM garbage; after forced GC,
retained heap was about 295–394 MiB while holding original and cloned documents,
analysis and display arrays. These are neither peak nor minimum requirements,
and retained objects/JIT/GC behaviour vary between runs.

## Bottlenecks and workarounds to evaluate

1. **Chart preparation and rendering dominate the main-thread pause.** The CPU
   profile for native 250k includes hundreds of milliseconds in Recharts grid
   text measurement (`getBoundingClientRect`), per-point object copying and GC.
   The installed Recharts `CartesianGrid.js` invokes its vertical coordinate
   generator even with `vertical={false}`. Its stack reaches `getTicks` and
   `getStringSize`; `Line.js` also constructs label-list entries for every point.
   These findings come from actual sampled stacks plus installed source inspection,
   not an assumption that SVG drawing alone is the cause.
   First evaluate explicit bounded grid ticks/avoiding unused grid calculation,
   and a width-aware derived chart dataset. Preserve endpoints, gaps, extrema,
   stop transitions and original sample identifiers. Keep all source measurements
   for analysis and exact selection. A simple every-Nth-point filter would lose
   important features and is not an acceptable final algorithm.
2. **The parser allocates a full DOM after already validating XML with SAX.**
   Explore building the canonical model directly from strict SAX events, then
   incremental `File.stream()` parsing if measurements justify it. This could remove
   the second parse and transient DOM allocation. Preserve malformed/hostile-input
   behaviour and immutable source retention; the current string-based original
   content interface needs deliberate handling if streaming changes it.
3. **Analysis and result copying grow with the source.** Analysis currently runs
   on the main thread, and the worker clones the original text plus canonical
   objects back. Evaluate worker-owned analysis/settings updates and reduced
   duplicate representations. Do not move display downsampling into the canonical
   data or drop source precision. Browser transfer-only and peak worker memory
   need more precise measurement before choosing a transfer format.
4. **Selection still triggers expensive chart work.** The 250k selection delay
   persists after import. Preserve a stable display dataset across selection
   changes and render a selected original sample independently. Profile click/tap,
   smoothing, units, map display and replacement too; this first latency series
   measures keyboard selection only. Map rendering has not been separately isolated.

The next implementation slice is chart display reduction and avoiding unnecessary
chart work, with full-resolution correctness tests. Re-run the same workloads and
interactions before claiming improvement. Parser/worker memory work follows the
measured evidence; no cap is authorised as a substitute.

## Coverage and remaining work

The complete permissioned Strava-derived fixture replaces the earlier excerpt.
All 8,142 points remain; coordinates, timestamps and elevations are synthetic,
and extensions are removed. Its memory/parse cost is consequently lower than the
private original. See [fixture provenance](../tests/fixtures/gpx/README.md).
Compatibility remains GPX 1.1 for the tested examples; GPSBabel GPX 1.0 is explicitly
rejected and sensor extensions are not interpreted.

Physical phones, Safari/Firefox, sustained thermal/memory pressure, richer vendor
extensions and high track/segment/waypoint counts remain evidence gaps. A narrow
single-segment synthetic benchmark does not establish universal large-file support.
O4 and the responsive large-file part of #4 remain open.
